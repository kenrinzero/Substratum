### 5. near-identical-siblings

**real-defect / legitimate-variant (three-of-a-kind refactor)** — the new "non-file ByteSource → temp file" staging block is now duplicated **three times** with no divergence except the temp-file suffix and the prefix. The 20-line block lives in:

- `_dolphin.py:78-95` (DolphinTool staging; suffix `.{format_tag}`)
- `wbfs.py:89-105` (wit staging; suffix `.wbfs`)
- `nkit.py:103-119` (NKit staging; suffix `.nkit.iso`)

All three follow the exact same shape: `if isinstance(src, FileSource): path = src.path; staged = False; else: NamedTemporaryFile(suffix=...); try: stream 1 MiB chunks; flush; path = Path(tmp.name); close; staged = True; except BaseException: close + unlink + raise`. The 1 MiB chunk and the `min(1 << 20, total - pos)` idiom are identical across all three. The error-cleanup pattern is identical. Only the suffix string differs.

This is above the "three or more sequential code blocks" threshold (`checklist.md:136`). The chd, three_ds_ncch_enc, three_ds_ncch_enc_seed audit precedent for the `_TempFileSource` triple (`AUDIT-2026-08-21-b.md:62-66`) is the *same shape* — three intentional duplicates because each layer was dispatchable on its own. **The same rationale does not apply here** for two reasons:

1. The `_TempFileSource` triple is `class` boilerplate (init/read_at/size/close/__enter__/__exit__), and an extra arg per class is a real difference. The staging triple here is **the same 20-line procedure with only the suffix string changing** — that's the textbook near-identical-sibling.
2. The new `_spool.py` module was extracted in this round specifically to share the lifecycle/cleanup shape; the staging block would be a natural sibling extraction in the same spirit, into something like `_stage.py` (a `stage_to_tempfile(src, suffix) -> tuple[Path, bool, Callable]` helper). The chd precedent did not have a shared module to migrate to; this one does, and the writer of the wbfs/nkit units just used a separate one (the lifecycle) but not the other (the staging).

**Triage decision:** real-defect, but in the "would shorten the file substantially" sense — the refactor is mechanical (pass a `suffix` parameter, return `(path, staged, cleanup)`) and the existing tests pin the behavior (the `wbfs` and `nkit` round-trip tests would catch any deviation in the staged-tempfile path). Filed for the Suggested Fix Order.

**Sibling-tool resolution (different concern, not a near-identical-sibling)** — `dolphin_tool_exe()`, `wit_exe()`, `nkit_tool_dir()` all follow the same "override → on_path → repo → raise" pattern, but each names a different env var, a different on-path key, and a different repo-relative path; they are sibling functions that share a control flow, not siblings that differ in one identifier. Same legitimate-variant as the chd/wit/dolphin-tool resolution precedent; left as-is. A `find_tool(env_var, on_path_names, repo_rel)` helper would shorten the file but the per-tool documentation is what makes each function usable; net wash.

### U-1. `zip.py:317` — `if not flags & _FLAG_DESCRIPTOR:` works by Python truthy/falsy accident

> **CORRECTION (2026-08-21, Claude Opus 5 — `AUDIT-2026-08-21-d.md` § B1). This finding
> is wrong. It is left below unedited as the record; do not act on it.**
>
> The premise inverts Python's grammar. `not` binds *looser* than `&`, so `&` groups
> first and `not flags & MASK` parses as `not (flags & MASK)` — the ordinary, correct
> idiom. Verified by AST:
> `not flags & MASK` → `UnaryOp(op=Not, operand=BinOp(flags & MASK))`.
> (The finding's own text is self-contradictory: it states "`not` has lower precedence
> than `&`" and then draws the conclusion that would follow from the opposite.)
>
> There was therefore no truthy/falsy accident and no maintainability hazard — the
> original expression was simply correct. The follow-on warning that a maintainer might
> write `if flags & not _FLAG_DESCRIPTOR:` and "silently flip the check" is also void:
> that expression is a **SyntaxError**, since `not` cannot be the right operand of `&`.
>
> The applied edit (`(flags & _FLAG_DESCRIPTOR) == 0`) is behaviour-identical and was
> left in place. The four-line comment it installed at `zip.py:317-322`, which asserted
> the false precedence rule next to the code, has been removed and replaced with a
> one-line comment describing what the guard is for.

```python
if not flags & _FLAG_DESCRIPTOR:   # zip.py:317
```

Python's `not` has lower precedence than `&`, so this parses as `if (not flags) & _FLAG_DESCRIPTOR:`. The author's intent was `if not (flags & _FLAG_DESCRIPTOR):` — "if the descriptor flag is NOT set, do the local-vs-central size check." Verified live via a small Python snippet that the current code happens to produce the correct truth value for both `flags = 0` and `flags = _FLAG_DESCRIPTOR` because:

- `not 0x0008` is `False` (= 0), and `False & 0x0008` is `0` → falsy → block skipped (correct: flag set → skip).
- `not 0` is `True` (= 1), and `True & 0x0008` is `0x0008` (= 2048) → truthy → block runs (correct: flag clear → run).

So the test suite passes today (`test_zip.py:115-121` round-trips the descriptor-flagged `DATA/SUB/C.DAT` member). The hazard is that **the code is working by accident of Python's truthy/falsy semantics, not by design**. A future refactor that:

- Changes `flags` to a `bool` (e.g., a `FlaggedBits` newtype), or
- Changes the precedence expectation (e.g., parenthesizes the expression to `if not (flags & _FLAG_DESCRIPTOR):` — which would still be correct), or
- "Optimizes" the expression by hoisting `not` outside the bit test (e.g., `if (flags & _FLAG_DESCRIPTOR) == 0:` — also correct)

…would either silently break or silently fix. A maintainer who adds explicit parens today gets the same behavior. A maintainer who reads the line and concludes "this is buggy" and "fixes" it to `if not (flags & _FLAG_DESCRIPTOR):` *also* gets the same behavior, by luck. A maintainer who flips the precedence to `if flags & not _FLAG_DESCRIPTOR:` would silently flip the check (it would become `if False & ...: run` and `if 0x0008 & True: run` which evaluates to the opposite).

**Triage:** Not a real-defect (the test suite proves the current behavior is correct), but a real **maintainability hazard**. The 4-check gate and the seedtool's 21 new tests cover the descriptor-flagged path. The honest fix is to add parens (or replace with `if (flags & _FLAG_DESCRIPTOR) == 0:`) and document the intent. This is the kind of thing the AUDIT-2026-07-30 "linter-found it" precedent captures — but the prior audits did not flag it, possibly because the descriptor-member test happens to pass.

**Filed for the Suggested Fix Order** under maintainability, not correctness.
