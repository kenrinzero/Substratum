## Findings by entry

### 1. swallowed-exceptions

**real-defect (NEW)** — `substratum/formats/chd.py:120`:
`except (subprocess.CalledProcessError, OSError, TimeoutError): return None`
in `_chd_tag`. The `TimeoutError` arm is dead: a `subprocess.run` timeout
raises `subprocess.TimeoutExpired`, whose MRO is
`(TimeoutExpired, SubprocessError, Exception, BaseException, object)` —
verified live on this machine's 3.13 — so it is caught by neither the
builtin `TimeoutError` nor `OSError`. Cue matched: handler returning `None`
from inside an `except` block whose stated contract (docstring lines
106-111 and the session log) is "fall back to the safe CD extraction path
instead of failing early." For the timeout failure mode the fallback never
happens: a 300 s `chdman info` stall escapes `_chd_tag` and aborts
`normalize_chd` entirely. The failure is loud, not silent, which is why
this is minor — but the code expresses intent to catch a timeout and
cannot. Fix: catch `subprocess.TimeoutExpired` (the other two arms can
stay).

The `CalledProcessError` / `OSError` arms themselves triage
**legitimate-variant (repeat-class)**: narrow predicate, documented
tool-boundary fallback, and the fallback's next step (`extractcd` with
`check=True`) re-fails loudly on genuinely broken media — no silent
success path. Prior repeats re-verified unchanged: `verify.py:88`
(frozen gate normalization boundary) and `wii_partition.py`
best-effort cleanup.

## Uncategorized observations

1. **`chd` → `ps1-bincue` composition still refuses through the public
   API — the fix's own consumer chain.** `ps1_bincue._resolve_pair`
   (`ps1_bincue.py:406-424`) requires a path or a `FileSource`; the
   ByteView returned by `normalize_chd` wraps a `_TempFileSource`, which
   is neither and exposes no path. Even with the now-correctly-named
   `extracted.cue`, `normalize(view.source)` raises "requires a path to
   the .bin." The BACKLOG's verified end-to-end (`chd → ps1-bincue →
   iso9660 → Stratum scan`) was path-based, not library-composed, and the
   open chd row itself flags this ("consider exposing the inner path").
   No gate test composes the two layers, so this class cannot fail the
   gate. The `f061cef` session log's "Fixed the chd defect chain" is true
   for dispatch + naming, but the consumer path is not yet reachable
   through `substratum.normalize`.

2. **The DVD dispatch branch is mock-only proven.** No DVD-type (PSP) CHD
   is staged under `fixtures/_local/` (`bin-chd-playstation` is CD-type),
   so `chdman extractdvd` never ran against real media in the gate — the
   mocked test simulates the tool, including the assumption that
   `extractdvd -o file.bin` writes the image directly to `-o`. The
   dispatch string (`Tag='DVD '`) is operator-verified real output, so
   misparse risk is low, but the command shape is unverified on media.
   The BACKLOG row staying open is consistent with this; the session log's
   "proven in the repo gate" should not be read as retail proof. Staging
   one PSP CHD (operator-gated) would close it the way Jade Empire closed
   xdvdfs.

3. **Retail XGD1 discs still mis-dispatch through the public dispatcher**
   (repeat-class of the 08-14 GD-ROM footgun, now a second instance).
   `normalize.py:103` registers `sniff_xdvdfs` with the default
   `base_offset=0`, so a redump XGD1 image — decoy DVD-Video partition
   first, game descriptor at `0x18310000` — falls through to `iso9660`
   and returns the decoy tree (BACKLOG: KotOR → 6 `.vob` files, "the
   worst failure shape for a census"). Callers must know to call
   `normalize_xdvdfs(source, base_offset=0x18300000)` directly. Unlike
   GD-ROM (where `lba_base` is self-described per-disc and heuristics were
   rightly rejected), the XGD1 game-area base is a fixed constant of the
   format generation — a registry-level sniff probe at the known base
   would be deterministic, not heuristic. Worth an explicit decision when
   the dispatcher question is next opened; until then the composition
   path lives only in NORMALIZERS/BACKLOG prose and the skipif test.

4. **Hardcoded personal path in a public test.** `tests/test_xdvdfs.py:45`
   probes
   `C:\Users\kenrin\Downloads\_tools\xdvdfs-rs\target\release\xdvdfs.exe`.
   It is `exists()`-guarded (CI skips cleanly) and `XDVDFS_EXE` takes
   precedence, but the middle candidate commits a machine-specific path —
   including the Windows username — to the public GitHub repo, and no
   other test hardcodes user paths (the established patterns are env vars,
   repo `tools/` vendoring, or `fixtures/_local`). Related: the xdvdfs-rs
   oracle is version-recorded but not vendored/provisioned the way
   chdman/wit/ctrtool are, so the retail proof is machine-bound to this
   one box.

5. **Stale docs (repeat of 08-14 observation 3, plus new instances).**
   `README.md:22` and `BACKLOG.md:10` still say 0.0.18 (code is 0.0.19).
   New with this session: `chd.py` module docstring (lines 6-8) and the
   NORMALIZERS chd row still say decompression "delegates to chdman via
   `extractcd`" — no longer true for DVD-tagged CHDs; and the
   `tests/test_xdvdfs.py` module docstring (lines 3-5) still says "no
   external differential tooling" while TOOLS and the manifest now carry
   the xdvdfs-rs differential. Also minor: `normalize_xdvdfs`'s
   `root_sector == 0` refusal reports "root directory size is invalid"
   (pre-existing message quirk, unchanged).

6. **CONTRIBUTORS.md has no row for the Copilot CLI identity** that ran
   the 2026-08-20/21 sessions (the two existing Copilot rows are other
   models). The atelier log records the sessions; the contributor list's
   own convention (agents listed by the identity they ran under) is
   missing this one. Operator knows the underlying model.

7. **Positive findings, for the record.** The xdvdfs fix is correct and
   honestly proven: the `*4` dword multiply pre-existed, so the actual
