## A. Contract-level findings

### A1. Directory entries violate the frozen contract's stated invariant — 97 of them, in 11 committed manifests

`substratum/contract.py:89` — the **frozen** module four downstream segments bind to —
documents `FileEntry.offset` as "byte range into the underlying source (**0 for dirs**)".

`substratum/formats/iso9660.py:158` emits directories with a real extent and length:

```python
entries.append(FileEntry(path, "dir", loc * block, size))
```

Every other tree normalizer honours the invariant — `gc_fst.py:139`, `wii_fst.py:159`,
`wii_u8_arc.py:93`, `xdvdfs.py:137`, `three_ds_romfs.py:246`, and `zip.py` all emit
`(0, 0)`. `iso9660` is the sole outlier, and because `chd`, `cso`, `ciso`, `ps1-bincue`
and `saturn-dc-raw` all compose *through* it, the divergence is baked into the committed
expected manifests of six units:

| manifest | dir entries | with non-zero offset/size |
|---|---:|---:|
| `iso9660/supertux` | 17 | 17 |
| `iso9660/synthetic` | 3 | 3 |
| `chd/supertux` | 17 | 17 |
| `cso/ape-escape` | 4 | 4 |
| `cso/synthetic` | 3 | 3 |
| `ciso/synthetic` | 3 | 3 |
| `ps1_bincue/kings-field` | 42 | 42 |
| `ps1_bincue/burstrick` | 1 | 1 |
| `ps1_bincue/synthetic` | 3 | 3 |
| `saturn_dc_raw/save-game-copier-3.7.1` | 1 | 1 |
| `saturn_dc_raw/synthetic` | 3 | 3 |
| **total (11 manifests)** | **97** | **97** |

Every directory entry produced by the ISO9660 family is affected — the two columns are
identical because no `iso9660`-derived directory carries `(0, 0)`.

**Why no audit caught it:** the four-check gate is structurally blind here.
`verify.run_checks` check 1 bounds-checks only `e.kind == "file"`; `sample_entries`
iterates `tree.files()`. Directory offsets are never validated and never diffed. And a
section-scoped audit sees one unit's self-consistent behaviour, not the disagreement
between six units and one comment.

**Why it matters now:** `DESIGN.md` §2 makes the manifest the downstream handoff shape
and the boundary is "contract types and manifests only". Stratum and Quarry are promoted
and will read these. Whichever way it resolves, resolving it after they ship code against
the invariant is far more expensive:

- If dirs are meant to be `(0, 0)` — `iso9660` has a bug and 10 committed manifests
  change (a manifest-format change across the whole ISO9660 family).
- If dirs may carry their own extent — that is arguably *useful* information, the
  `contract.py` comment is wrong, the schema should say so, and the other five walkers
  are discarding it.

Note `DESIGN.md` §1 itself is silent on the point; only the frozen module's inline
comment states the invariant. **This is the one finding worth settling before anything
else.**

### A2. Six committed `expected.manifest.json` files do not conform to `schema/manifest.schema.json`

Validated all 33 committed manifests against the schema: **27 conform, 6 do not.**

| file | violation |
|---|---|
| `fixtures/3ds_cia/biohazard/` | no `entries`; extra `identity`, `oracle`, `sections` |
| `fixtures/3ds_ncch_enc/biohazard/` | no `entries`; extra `identity`, `oracle`, `regions` |
| `fixtures/3ds_ncch_enc/kobayashi/` | same |
| `fixtures/3ds_ncch_enc_seed/boxboxboy/` | same |
| `fixtures/3ds_ncch_enc_seed/mini-sports/` | same |
| `fixtures/wii_partition/munchables/` | no `format`, no `source`, no `tool_versions`, no `entries` — an entirely different document (`generator`/`layout`/`samples`/`source_iso`) |

These are hand-written provenance/anchor records, and as records they are good — they
carry the oracle rationale, the crypto variant, the product code. The problem is that
they occupy **the canonical manifest filename**, so `expected.manifest.json` now means
two incompatible things in this repo: 27 schema-governed documents that
`verify.run_checks` check 2 byte-compares, and 6 free-form notes nothing validates.

The schema declares `"additionalProperties": false` and requires `entries`, so this is
not a permissive-superset situation — the six are invalid, not merely extended. And the
same *unit* can have both shapes: `3ds_cia/synthetic` conforms; `3ds_cia/biohazard` does
not.

Sixteen test modules validate a manifest against the schema; the ones that don't map
exactly onto the keyed/ByteView units (`test_3ds_cia`, `test_3ds_ncch_enc`,
`test_3ds_ncch_enc_96`, `test_3ds_ncch_enc_seed`, `test_wii_partition`, plus
`gcz`/`rvz`/`wbfs`/`nkit`, which ship no manifest at all). So the divergence is
un-guarded by construction: no test asserts that every
`fixtures/**/expected.manifest.json` validates.

**Cheapest fix:** rename the six to `anchor.json` (or `provenance.json`), and add a
one-line conformance test that globs `fixtures/**/expected.manifest.json` and validates
each. That test is the durable guard; without it the next keyed unit repeats the shape.

### A3. Composed-chain manifests are labelled by the outer container, not by the layer that produced the entries

`fixtures/chd/supertux/expected.manifest.json` declares `"format": "chd"` over 796
ISO9660 entries; `fixtures/ciso/luigi` declares `"format": "ciso"` over 911 gc-fst
entries. This comes from the test wrappers, e.g. `test_ciso.py:92-95`:

```python
tree = normalize_iso9660(view.source)
return FileTree(source=tree.source, format="ciso", entries=tree.entries)
```

As a way to pin a chain in a fixture this is fine and deliberate. But `normalize_chd`
and `normalize_ciso` return `ByteView`s and never emit a `FileTree` with that format id,
so a downstream consumer reading `format` as "which normalizer produced these entries"
is misled. Not a defect; worth one sentence in `DESIGN.md` §2 saying `format` on a
composed manifest names the *chain*, keyed by its outermost layer.

## B. Process and documentation findings

### B1. `AUDIT-2026-08-21-c.md`'s U-1 finding is factually wrong, and its wrong reasoning is now a permanent comment in production code

The memo states:

> Python's `not` has lower precedence than `&`, so this parses as
> `if (not flags) & _FLAG_DESCRIPTOR:`

Both halves cannot be true together, and the conclusion is the wrong one. `not` binding
*looser* than `&` means `&` groups first. AST-verified:

```
not flags & MASK  ->  UnaryOp(op=Not, operand=BinOp(flags & MASK))
```

`not flags & _FLAG_DESCRIPTOR` is `not (flags & _FLAG_DESCRIPTOR)` — the ordinary,
correct idiom. There was no truthy/falsy accident, and no hazard. The memo also warns
that a maintainer might write `if flags & not _FLAG_DESCRIPTOR:` and "silently flip the
check"; that expression is a **SyntaxError** in Python, so it cannot silently do
anything.

The applied edit is behaviour-neutral and harmless in itself. What is not harmless is
the four-line comment it installed at `substratum/formats/zip.py:317-322`, which now
teaches the false rule permanently, in a public repo, next to the code:

```python
# Written as (flags & MASK) == 0 (not `not flags & MASK`,
# which parses as `(not flags) & MASK` and only happens to do the
# right thing by Python's truthy/falsy semantics).
```

**Fix:** delete lines 317-322 and keep a one-line comment on what the guard is *for*
(descriptor-flagged members carry zeroed local sizes). Correct the U-1 section of the
`-c` memo, or annotate it as withdrawn, before that memo is committed.

### B3. Convention drift: two modules written the same day answer "can I get a path from this source?" opposite ways

- `ps1_bincue._resolve_pair:414` — `if hasattr(source, "path")` (deliberately widened
  on 2026-08-21 so a `_TempFileSource` from a CHD decode could resolve its sibling
  `.cue`).
- `_stage.stage_to_tempfile:46` — `if isinstance(src, FileSource)`.

`TempFileSource` is not a `FileSource` subclass; it *wraps* one and exposes `.path`.
So passing a `TempFileSource` — which is what **every** `chd` / `rvz` / `gcz` / `wbfs` /
`nkit` decode returns — into `normalize_wbfs`, `normalize_nkit` or `convert_disc_to_iso`
streams the entire decoded image through Python into a second temp file, when the path
was already on the object. On a 4.7 GB Wii image that is a needless full copy.

Not currently on a hot path (the shipped `zip → rvz → gc-fst` chain hands over a
`SliceSource`, which genuinely has no path and *must* be staged), so this is latent.
Making `stage_to_tempfile` duck-type on `.path` the way `_resolve_pair` does closes it
and unifies the convention.

### B7. Twelve tracked files carry CRLF, and `.gitattributes` guarantees they keep it

`AGENTS.md` and the atelier charter both require LF. `.gitattributes` sets `* -text`,
which disables all end-of-line conversion — correct for a repo whose premise is
byte-exactness, but it means **whatever line endings are committed are permanent**: Git
will never normalize them on checkout or check-in. Twelve tracked files are committed
with CRLF:

| file | kind |
|---|---|
| `BACKLOG.md`, `NORMALIZERS.md`, `README.md`, `fixtures/zip/retail/README.md` | docs |
| `substratum/formats/chd.py`, `substratum/formats/xdvdfs.py` | source |
| `seedtools/make_xdvdfs_fixture.py`, `tests/test_chd.py`, `tests/test_xdvdfs.py` | source |
| `fixtures/wii_fst/synthetic/payloads.json`, `fixtures/wii_partition/synthetic/clusters.json`, `fixtures/wii_partition/munchables/anchor.json` | fixture data |

Verified per-file against `HEAD`: all twelve are pre-existing, none introduced by this
session's edits.

**RESOLVED in a follow-up commit** (see the Remediation section). The table above was
also incomplete: the sweep behind it only looked at `.md`/`.py`/`.toml`/`.json`, and a
full census over every tracked file found **21** genuine CRLF text files, not twelve —
the extras being `fixtures/ps1_bincue/synthetic/game.cue` and eight files under
`reference/` directories.

The root cause turned out to be mechanical rather than incidental: four seedtools write
their text artifacts with `Path.write_text`, which maps `\n` to the platform newline on
Windows. That is precisely the hazard the atelier charter's newline-translation caution
names, and it means the affected files would have regressed to CRLF on the next
regeneration no matter how often they were normalized by hand.

The eight files under `reference/` are **correctly** CRLF and were left alone: they are
the independently-extracted bytes gate check 4 diffs entry payloads against, and PS1
`SYSTEM.CNF` and the SuperTux `.STL` levels genuinely carry CRLF *inside the disc image*.
Rewriting them would falsify the oracle — and, usefully, would also fail the gate, since
the tree read would no longer match.

No test pins `_FORMATS` **order**, either — the ordering is load-bearing five times over
and is currently protected only by per-unit sniff tests, which cover it for the pairs
their authors thought about.

### C2. `cia` before `3ds-ncch-enc-seed` is an undocumented load-bearing ordering

The sniff sweep found `fixtures/3ds_cia/synthetic/game.cia` claimed by **both** `cia`
and `3ds-ncch-enc-seed`. Dispatch is correct today only because `cia` is registered
second and `3ds-ncch-enc-seed` third. `normalize.py` carries explicit comments for its
other four order-dependencies (ciso/cso, nkit/gc-fst, enc-96/enc, enc/ncch); this fifth
one has none, so it is the one a future reordering breaks.

(The sweep's other multi-claim — `3ds-ncch-enc-96` and `3ds-ncch` both claiming
`encrypted.ncch` — is correct and already documented at `normalize.py:91-95`.)

Root cause of the loose sniff is worth noting: `three_ds_ncch_enc_seed.sniff:194-208`
gets a `ByteSource`, reads the header through it via `_is_cia`, then calls
`_content_offset(cia_path)` which **re-opens the file from a path** and reads the same
header again. Because of that it must `return False` for any non-`FileSource` — so a CIA
arriving as a `ByteView`/`SliceSource` from a composed layer can never be sniffed. Passing
the `ByteSource` through instead of the path removes both the double read and the
limitation.

### C3. Executable-pin completeness test covers 7 of 9 vendored tools; NKit has no exe pin at all

`test_tooling_hardening.py:35-46` asserts pin completeness over `CHDMAN`, `WIT`,
`MAXCSO`, `ECM`, `UNECM`, `CTRTOOL`, `THREEDSTOOL`. Since it was written,
`vendor_tools.py` gained two more vendored tools:

- **DolphinTool** — has `DOLPHIN_TOOL_EXE_SHA256:107`, but is not in the test's tuple.
- **NKit 1.4** — has **only** `NKIT_ZIP_SHA256`. There is no `NKIT_EXE_SHA256`.

The archive pin is well done (cross-checked against the AUR package's independent pin, so
two parties agree on the bytes) and it transitively covers extraction, because
`check_pin(zpath, …)` runs before `extractall`. The gap is the **fast path**:

```python
def vendor_nkit() -> None:
    exe = TOOLS / "nkit" / "ConvertToISO.exe"
    if exe.is_file():
        print("nkit already vendored (…)")
        return          # <-- no hash check, and none is possible: no exe pin exists
```

`vendor_chdman:166`, `vendor_wit:204` and `vendor_maxcso:237` all call
`check_pin(exe, …)` on exactly this branch. NKit is the only one that verifies nothing —
and it is the tool fetched from a Referer/UA-gated forum download URL
(`gbatemp.net/download/nkit.36157/download?version=36607`), the least stable and least
authenticated of the nine sources. `AGENTS.md` §5 requires that "a re-run on a drifted
binary must fail loudly"; for `nkit` it re-runs silently.

**Fix:** add `NKIT_EXE_SHA256`, call `check_pin` on the already-present branch, and add
both it and `DOLPHIN_TOOL_EXE_SHA256` to the completeness tuple.

## D. Low severity / hardening

- **D1.** `zip.sniff:410` and `three_ds_romfs.sniff:263` catch `(ValueError, OSError)`,
  but their parsers use `struct.unpack*`, and `struct.error` derives from `Exception`,
  **not** `ValueError`. A sniffer that raises aborts the whole dispatch loop instead of
  falling through to the next format. Empirically clean today (the sweep raised nothing
  across all 25 committed fixtures); adding `struct.error` to the tuple is a one-word
  hardening.
- **D2.** Five of six tree walkers recurse: `gc_fst._recurse`, `wii_fst._recurse`,
  `wii_u8_arc._recurse`, `three_ds_romfs.walk_dirs`, `xdvdfs._walk_table`. Only
  `iso9660._walk` uses an explicit stack. `xdvdfs` is the sharpest — it recurses per
  **right sibling** (`xdvdfs.py:158`), not just per subdirectory, so a degenerate LCRS tree costs
  one stack frame per entry rather than one per depth level. `RecursionError` is caught
  by the gate as a structural red, so this is robustness, not a crash.
- **D3.** `ciso.py:172-174` computes `needed` treating the final block (2241) as a
  256 KiB partial slot, while `_CisoSource.read_at:105` addresses every slot as a full
  2 MiB. Unreachable on GC content (the tail blocks are absent, as the docstring says),
  but the two halves disagree and would refuse a full-size image.
- **D4.** `xdvdfs.py:140-143` raises one of two different messages for the *same*
  condition, selected by `file_size <= _SECTOR * 4` — an error string chosen by payload
  size rather than by cause. Reads as fitted to a test expectation.
- **D5.** `three_ds_romfs._verify_hash_tree:103` docstring says "Streaming, bounded RSS"
  but reads the entire level-0 and level-1 hash tables into memory (`O(data/block)` —
  ~32 MB for a 4 GB RomFS at 4 KiB blocks, more at smaller block sizes). The per-block
  reads *are* streamed; the claim overstates.
- **D6.** `three_ds_romfs.py:248` — `off = tables.dir_entry(off)[1]` re-parses an entry
  whose sibling field was already unpacked as `_c_sib` nine lines earlier.
- **D7.** `rvz.py:29-31` requires `size() >= 4` but compares only 3 bytes (`b"RVZ"`),
  leaving the version byte of the `RVZ\x01` magic unchecked — against the house rule
  stated in `nkit.py:80-83` that short signatures need corroboration.
- **D8.** `docs/superpowers/specs/` holds seven unit design specs, all dated
  2026-07-22..24, and nothing for the sixteen units since. A harness-named directory
  tracked in a public repo, with no README saying what it is or that it stopped. Fold
  into `docs/specs/` with a note that it covers the early units only, or drop it.
- **D9. Scope of the fidelity evidence** (settled policy, `DESIGN.md` §3 — recorded so
  the strength of a "green" is not overstated): check 4 diffs **16 files per fixture**.
  On the largest trees that is 16 of 911 (`ciso/luigi`), 16 of 796 (`iso9660/supertux`),
  16 of 550 (`cso/ape-escape`), 16 of 470 (`ps1_bincue/kings-field`). The complete
  independent extractions are already on disk (847, 779, 546, 428 files respectively),
  so an opt-in env flag lifting `SAMPLE_CAP` for a periodic deep run would raise
  byte-level coverage from ~2% to 100% on those anchors at zero authoring cost.

## Summary

The project is in good shape and the gate is honest: **495 passed, 0 failed, 0 skipped**
on the current tree, with a fidelity check that genuinely bites and a fixture policy that
has not leaked a single retail byte into git across 24 units.

The findings that matter are the ones only a whole-repository pass produces. **A1**
(directories) and **A2** (manifest shapes) are both *divergences between units that are
each internally consistent* — every section audit correctly saw no local problem, because
there isn't one; the problem only exists in the comparison. **B1** is a different class
and worth naming plainly: an audit finding that was wrong on the language semantics, was
applied, and left the error behind as a comment in shipped code — the reason a final pass
should re-derive claims rather than inherit them.

Nothing found is a correctness bug in a normalizer's byte handling. The two contract
findings are decisions, not repairs, and taking them now is much cheaper than taking them
after the downstream segments bind.

**New finding, surfaced by that test — `3ds-ncch-enc-seed` is unreachable by
auto-detection.** Its sniffer accepts a CIA and nothing else, and `cia` is registered
ahead of it, so every source it could claim is claimed first (verified on the synthetic
CIA and both retail eShop anchors). This is correct — the documented path is walk the CIA,
then decrypt the selected content — but it means the sniffer can never fire, which is
exactly the kind of thing a later reader "fixes" by reordering the registry and silently
breaks CIA walking. Now documented in `normalize.py` and pinned by
`test_the_seed_unit_is_pin_only`. It also corrects this memo's own C2, which described
the ordering as merely load-bearing; it is stronger than that. (The related case
`3ds-ncch-enc` is auto-dispatchable, but on an encrypted NCCH *slice*, not on a whole CIA
— the CASES table now uses the on-media content blob.)

**Encoding (B7), in its own follow-up commit.** Root cause first: four seedtools wrote
text artifacts with `Path.write_text`, which translates `\n` to the platform newline on
Windows, so hand-normalizing the files would have regressed on the next regeneration.
Those four now `write_bytes`. Thirteen files converted CRLF → LF (nine source/docs, three
generated JSON descriptors, one `.cue`); the eight files under `reference/` deliberately
left alone, since their CRLF is what the disc image actually contains and rewriting them
would falsify the oracle. New `tests/test_encoding_conformance.py` enforces all of it:
UTF-8 everywhere, LF outside `reference/`, an AST guard against any `write_text` /
`open(...,"w")` without an explicit `newline=`, and — because an exemption nobody checks
is a hole — a test asserting that the `reference/` files *still* carry their original
CRLF, so a future "cleanup" that normalizes an oracle gets caught. Red-teamed all three
directions. Also closes **A3**: `DESIGN.md` § 2 now records that a composed manifest's
`format` names the chain by its outermost layer, and that `anchor.json` is the
deliberately schema-exempt sibling. **Gate after the encoding pass: 784 passed, 0 failed,
0 skipped, 19:45** (592 → 784; the encoding sweep parametrizes per file).
